# Release Pipeline

Use this skill from the `chill-vibe` repo root when the task is not just “run tests”, but “safely turn the current checkout into a shipped GitHub release”.

Reuse the verification posture from `../chill-vibe-full-regression/SKILL.md`, but own the full release chain: pre-flight → diff audit → final version bump → exact-tree verification → local `main` integration → push/convergence proof → tag/release (server-side build) → asset verification.

**Primary asset path: pushing the `v*` tag triggers `.github/workflows/release-zip.yml`, which builds the Windows zip server-side, uploads the canonical `Chill.Vibe-<version>-win.zip` (spaces normalized to dots), and verifies asset state + download URL itself — normally within ~3–4 minutes.** Do NOT build the zip locally or `gh release upload` manually on the happy path; that wastes minutes and races the workflow (HTTP 404/409). Local build is a fallback only (step 6b).

## Workflow

1. Pre-flight — inspect repo state and rule out interference before touching anything:
   - On Windows PowerShell 5.1, read repo text with `Get-Content -Encoding UTF8` (or a native file-read tool). Bare `Get-Content` decodes BOM-less UTF-8 through the system ANSI code page and can turn Chinese release rules/SPECs into mojibake before the audit even starts.
   - `git status --short --branch`, `git diff --stat`, `git remote -v`, `gh auth status`
   - `git fetch origin main`; record `git rev-parse main` and `git rev-parse origin/main`. The release target is the local `main` branch. If local `main` is behind or diverged, reconcile it before assembling a candidate; do not build a new release on a stale branch graph. A one-off `schannel: failed to receive handshake, SSL/TLS connection failed` from this fetch is transient TLS noise, not an unreachable remote — cross-check with `gh release list` (a different transport) and retry the fetch later; v0.19.1 hit it in pre-flight while `gh` worked and every later fetch/push succeeded.
   - read `package.json` version and `git tag --sort=-version:refname` (top few), then check the authoritative remote state with `gh release list --limit 5` or `git ls-remote --tags origin`; local tags can diverge from GitHub and the package version can lag an already-published release, so choose the next version above the highest published remote tag instead of trusting either source alone
   - if `git fetch --tags` reports `would clobber existing tag`, do not force-rewrite tags during the release. Record the mismatch, use the remote tag/release state for versioning and collision checks, and leave unrelated local tag repair for a separate task.
   - **Free port `5173` before launching anything long.** `playwright.config.ts` starts its web server with `--strictPort` and `reuseExistingServer` off by default, so any occupant makes the Playwright stage fail — but only after the gate has already spent ~20 minutes on the stages before it. Check `netstat -ano | Select-String ':5173'` in pre-flight, not as mid-run recovery. The common occupant is an **orphaned repo-local Vite** (`node scripts/run-vite.mjs`) whose parent CLI has exited; prove it with `Get-CimInstance Win32_Process` (command line matches `run-vite.mjs` **and** the parent PID no longer exists), then stop that one PID. An occupant that fails either half of that proof is somebody else's — leave it and follow the port-blocked path in step 4.
   - **The concurrency check is not a one-time gate — re-run it immediately before the version bump, before launching the release gate, and again before committing.** A pre-flight that comes back clean only proves nobody was writing *at 00:58*. v0.20.6 audited a quiet tree for 20 minutes, and while the audit fixes were being written another agent started a fourth slice in the same checkout: four files appeared or changed between 01:15 and 01:22 (`server/automation-board-mcp.js`, `server/automation-board-runtime.ts`, `tests/automation-board-mcp.test.ts`, plus new `docs/specs/workspace-admin-await-sessions/`), and the dirty-path count went 85 → 97. Worst of all, `shared/schema.ts` — an already-audited candidate file — grew that slice's `workspaceAdminAwaitDefaultTimeoutMinutes`, so the two slices could no longer be separated *by path* and the earlier audit verdict on that file was void. The cheap detector is a 45 s mtime resample over the non-candidate dirty files; the expensive alternative is discovering it after `git commit -a` has swallowed somebody's half-written slice. When this fires, the release is **blocked** per step 2's WIP rule — do not stash, revert, or hand-pick another agent's work to unblock yourself; report it and stop.
   - **Concurrency check: `git reflog -8`, recent dirty-file mtimes, and live repo-launched provider sessions.** For provider sessions launched *inside* the packaged app, "process exists" is not "agent is working": sample `(Get-Process -Id $pid).CPU` twice a few seconds apart — an idle session moves ~0.05s, an active one moves seconds. Idle sessions plus quiet mtimes mean you can work in the primary checkout instead of paying for an isolated worktree. Reflog only records ref movement; it does not reveal another card/agent that is still editing the shared working tree. If recent writes or multiple active Codex/Claude app-server sessions make concurrent work plausible, do NOT run long verification in the main checkout — a concurrent agent can switch HEAD or mutate files mid-run, so a long release gate can silently validate the wrong tree (happened for v0.17.11). Instead, create a repo-external worktree from the recorded local `main` commit: `git worktree add -b release/vX.Y.Z <external-path> <local-main-commit>`, install there, snapshot the audited candidate only after its source mtimes are stable, and prepare/verify it there. When moving an uncommitted candidate into that worktree, write the patch with Git itself (`git diff --binary --output=<repo-external.patch>`) and apply it with `git -C <worktree> apply --index`; do not pipe through PowerShell `Set-Content`, which can add a BOM and make every hunk fail to apply. **That worktree is verification isolation only: it must never run `git push origin HEAD:main`, create the final tag, or publish the release.** Final integration and publication return to the primary local `main` checkout after concurrent writes stop.
2. Audit the pending diff for release blockers before any commit:
   - look for secrets, tokens, auth headers, local absolute paths, debug-only noise, or unrelated files
   - treat obvious test fixtures like `sk-test` as expected only if they stay inside tests
   - **judge local paths and usernames against the remote baseline, not against a regex.** This repo legitimately carries `D:\Git\chill-vibe` in dozens of test fixtures, so a raw grep drowns you in false positives while a genuinely new leak hides in the noise. Diff instead: `git grep -l <token> origin/main` — zero hits on the remote plus hits in the candidate is the finding. That is how v0.19.0 caught a bench script hardcoding `C:/Users/<name>/AppData/...` into a public repo.
   - **run `pnpm test` (Node suite only) as a pre-check here, during the audit, before the version bump.** It is minutes, not the full gate, and it is the cheapest moment to absorb a red test: the version is not set yet, so no fingerprint is wasted. Expect one specific shape — a candidate that intentionally replaces a **source-shape guard** (for example a synchronous `try/catch` around an `ipcMain.on` listener, superseded by a shared sync/async error guard) shows up as exactly one red guard test. Update the guard assertion in the same candidate, then reverse-verify it (regress the implementation, confirm the test goes red, restore) — a source-shape guard that was never proven red is decoration.
   - **Audit whether the candidate's code is *correct*, not just whether it leaks — and do it with parallel subagents, because it is the one thing no gate does for you.** Every rule below this one is about the harness (stale assertions, SPEC drift, secrets); none of them asks "does this change do the right thing". v0.20.5 arrived with every gate green and still carried four real bugs, two of them the exact class the candidate existed to prevent: the new updater armed its rollback flag *after* the `Move-Item` pipeline (so a mid-swap failure skipped rollback entirely and left a half-emptied install — the very "install destroyed, no way back" scenario the slice was written to kill), and the new board-template sync switched models through `selectCardModel`, which also writes `settings.requestModels` / `lastModel` / `column.model` — so a **background, unattended** trigger silently rewrote the user's global default model. Both were invisible to Node, Playwright, Electron and quality.
     Fan out three read-only subagents over the candidate diff and wait for all three: (a) **source correctness** — every new/changed module, told to report only failures it can describe as concrete input → wrong output; (b) **stale Playwright assertions** — the sweep in the rules below; (c) **SPEC/docs** — task lists, version tags, cross-reference numbering. They take ~10-20 minutes wall-clock in parallel. Fix what (a) reports with the repo's red→green rule, then re-verify: a correctness fix at audit time costs one narrow test run; the same bug found after release costs a hotfix. v0.20.6's (a) found a P0 with a reproduction attached — the new `usageTotals` field was dropped by `normalizePersistedSessionHistoryEntry`, a逐字段 normalizer, so the release's headline feature died on restart while every gate stayed green.
     - **Subagent (b) reasons statically and cannot see the rendered page, so treat its hit list as "specs to run", never as "specs to rebaseline".** All three of v0.20.6's predicted stale snapshots (`settings-panel-card-stack`, `slash-menu-short-pane`, `pane-split-layout`) ran **green** — the author had already rebaselined what actually moved, and one prediction rested on a false premise (`slash-menu-short-pane` renders no empty-state tool grid at all, because triggering the menu types `/` into the composer and a non-empty draft hides the grid). Blindly running `--update-snapshots` on its list would have shipped three needlessly churned baselines and one bogus `toHaveCount` assertion. Cost of proving it: one `-g` filtered run per prediction, ~30 s each.
     - **Report the same care about (a): its P2/P3 findings are worth fixing, but verify each one against the code before writing a fix** — (a) also reasons from reading, and a "wrong order" claim that turns out to be intentional wastes a red→green cycle.
   - **First run the cheap triage that decides whether the six stale-Playwright rules below even apply.** They exist because a UI-shaped candidate hides breaks that only surface at minute 20 — but a candidate that touches no rendered output pays nothing for them, and you should be able to say so in two greps rather than re-reading six paragraphs. The candidate is out of scope when all three hold: (1) no CSS class / role / `data-*` selector added or stopped rendering (`git diff -U0 -- 'src/**/*.tsx'` and read the JSX-emitting lines, not the comments); (2) no **existing** default changed value in `shared/default-state.ts` / `shared/schema.ts`; (3) no `disabled` / `checked` / visibility condition changed on an existing control. v0.20.4 cleared all three in ~3 minutes and its Playwright stage passed first try. Watch the sharp edge in (2): **adding a new optional field whose default reproduces the old behaviour is not a default flip** (`wakeTimerAutoActivated: false` = "treat as user-opened" = exactly what every pre-existing card already did), whereas changing an existing field's default is one no matter how small the diff looks.
   - **a feature that adds, removes, or *replaces* one UI element breaks Playwright in two ways that no Node or quality gate can see**: hard-coded `toHaveCount(n)` assertions, and every screenshot whose frame contains the changed element. v0.19.0 inherited 13 stale counts and 26 stale snapshots from an already-merged feature branch; v0.20.0 inherited one more from a *replacement* (a bare `automation-board-item-toggle` checkbox swapped for the richer `WakeTimerSettingsPanel`), which the old "adds an element" wording did not flag. All of them were invisible until the 4-minute Playwright stage ~20 minutes into the gate, and each one costs a full re-gate because the fix changes the fingerprint. Before launching the gate, list the CSS classes/roles the candidate added **or stopped rendering**, then grep every `*.spec.ts` for counts of those selectors.
   - **an interaction-state change is the same class of hidden Playwright break even when the element never changes.** v0.20.3 made a pending wake-timer condition editable; the selector and count stayed identical, but `theme-check.spec.ts` still required `toBeDisabled()` and its screenshots still showed the locked copy. Whenever a candidate enables, disables, locks, unlocks, hides, or reveals an existing control, grep the specs for `toBeDisabled`, `toBeEnabled`, `toBeChecked`, visibility assertions, and snapshots framing that control before the full gate.
   - **a flipped default value is a UI removal, and it hides from the selector grep above.** v0.20.2 flipped `automationBoardCardEnabled` from `true` to `false` (shipping the board as experimental); no selector was added or removed, so grepping the candidate's CSS classes found nothing — yet `tool-card-settings.spec.ts` asserted `toHaveCount(4)` quick tools and `toBeChecked()` on a toggle it never names in the diff. Whenever the candidate changes a **default** in `shared/default-state.ts` / `shared/schema.ts`, grep the specs for the *consequences* of that default (counts, `toBeChecked`, and every snapshot whose frame contains the affected control), not for the field name — most specs that break never mention the field.
   - **the candidate's own fix for a flipped default is systematically incomplete — audit it as if it were untouched.** v0.20.2 arrived with `tool-card-settings.spec.ts` and `theme-check.spec.ts` already updated, which reads like the work is done; `card-title-editing.spec.ts` was still red, because its `createToolLauncherState` helper builds state through `createPlaywrightState` → `appStateSchema.parse` and therefore inherits every default without ever naming the field. The reliable sweep is over the **counting locator**, not the field: grep every spec for the locator whose count changes (`.chat-empty-tool-button` here), then open each helper that feeds it. Fix by turning the flag back **on** inside "all entries visible" helpers rather than lowering the number — the assertion's intent is a worst-case layout, and keeping it at 7 also keeps that spec's snapshots unchanged.
   - **"only one snapshot went red" is a warning, not a clean bill of health — the rest are probably sitting on the tolerance edge.** v0.20.5's candidate collapsed the template pill's idle chrome with `max-width: 0`, which changes the pill's actual width; all six whole-board snapshots drifted, but five stayed under `maxDiffPixelRatio` and only one was judged red, so the candidate shipped five stale-but-passing baselines that would flip on any machine with slightly different font rendering. When a candidate touches geometry, rebaseline the whole group and read `git status`: if only the already-red ones move, the group is genuinely consistent; if others move too, they were riding the tolerance. (The root cause is worth fixing rather than rebaselining around — collapsing idle chrome must use `opacity`/`visibility`, never anything that changes layout.)
   - **That rebaseline needs `--update-snapshots=all`; the bare flag cannot do it.** Playwright ≥1.49 defaults `-u` to `changed`, which rewrites only the baselines it already judged *different* — precisely the ones NOT riding the tolerance. v0.20.6 widened a stats-card subtitle by three CJK characters, the spec carries `maxDiffPixelRatio: 0.01`, and a bare `--update-snapshots` run reported "4 passed" while leaving all three PNGs **byte-identical** (verify with `Get-FileHash`, not with the pass count — a tolerance-absorbed diff looks exactly like a no-op). `--update-snapshots=all` rewrote them. Rule: whenever the candidate provably changed what a snapshot renders, rebaseline with `=all` and diff the hashes; a green `-u` run is not evidence the baseline is current.
   - **run the specs you just repaired before launching the 20-minute gate.** Fixing a stale count/snapshot changes the fingerprint anyway, so the marginal cost of proving the repaired specs first is ~4 minutes against a full re-gate. v0.20.2 ran `theme-check` + `card-title-editing` + `tool-card-settings` (207 tests, 4.2 min) and entered the release gate already knowing the Playwright stage would pass.
   - **a default flip also reaches specs the changed control merely appears *behind*, and the Electron stage where the control is a click target.** Even after the targeted sweep above, v0.20.2's gate still surfaced two more: `model-menu-short-pane-{dark,light}.png` differed by 2536 px (4%) purely because the removed quick-tool brick sits in the screenshot's background, and `electron-automation-board-restart-runtime.test.ts` seeds state from `createDefaultState` and then clicks that brick by name — it burned a 32 s timeout that reads like a persistence regression. So extend the sweep twice: (1) every snapshot whose *frame* contains the control, not just the ones whose subject it is — rebaseline those with a single-spec `--update-snapshots` and confirm via `git status` that only the expected PNGs moved; (2) every Electron runtime test seeding from `createDefaultState`, which inherits new defaults silently. Both fixes are cheap; finding them at minute 20 is not.
   - **the SPEC verification records in the candidate are per-slice and go stale when two slices share one checkout.** The wake-timer slice honestly recorded "未跑 test:theme：本次只改了 tooltip 文案"; the automation-board slice in the same working tree had meanwhile rewritten a settings group label. Neither author was wrong, and the merged claim was. Read the verification records as evidence about *their own slice only*, and re-derive the visual/gate impact from the combined diff.
   - when a stale count is confirmed, **do not just change the number**. The old assertion's intent was "these controls exist"; `toHaveCount(2)` → `toHaveCount(1)` also passes when the replacement never renders at all. Assert the successor alongside the survivor, then reverse-verify it (disable the successor, confirm red, restore) — the same red-first rule the repo applies to product code applies to a gate you just weakened.
   - explicitly review new docs/spec files so accidental scratch notes do not ship
   - audit test registration before trusting any green suite: every new ordinary `tests/*.test.ts(x)` file must be imported by `tests/index.test.ts`; dedicated Electron runtime/performance files must instead be listed in `scripts/run-electron-runtime-tests.ps1`. Run the new proving files narrowly after registration; an unregistered red test is invisible to `pnpm test:release`.
   - treat changed SPEC task lists with unchecked implementation/verification boxes as a release blocker until the corresponding slice is completed or explicitly excluded; run any newly added proving test narrowly so an intentional red test cannot hide inside the later full-suite output. **Verify each unchecked box against the code before believing it** — a task list is written before the work and updated by whoever remembers to. In v0.19.0 the two scariest unchecked items (quit handshake, mixed-handler split) were both fully implemented and only the checkbox was stale, while a different slice really was deferred. Blocking on a stale checkbox is as wrong as shipping on a stale green one; resolve the ambiguity by reading the implementation, then fix the SPEC in the release commit and state the delivered scope explicitly.
   - if the checkout mixes a release-ready slice with unfinished user/agent WIP, preserve the WIP on a named branch/worktree and make local `main` release-ready before publication. A repo-external release worktree may assemble and verify a path-limited candidate, but it does not make remote-only publication safe. Do not stash, revert, discard, or accidentally commit excluded WIP; if local `main` cannot safely become clean and accept the candidate, the release is blocked.
   - if something is suspicious, stop and fix or exclude it before continuing
3. Set the final release version after the audit and before the final verification:
   - **default to the next patch version. "This release has a lot of features" is NOT a reason to bump the minor.** The owner reserves the minor position for two things only: a major *stability* milestone (v0.19.0 moving the whole backend into a utilityProcess is the reference case), or a batch of accumulated patch releases that deserves a marker. v0.20.0 was bumped on feature volume — new board UI plus a never-working MCP surface finally connecting — and the owner corrected it on the spot. When in doubt, ship a patch: an extra patch costs nothing, a premature minor spends a milestone slot.
   - update `package.json` and any other repo-owned version references that must stay in sync
   - stage the version bump together with the already-audited product changes
   - the final release verifier fingerprints the complete tree, so changing the version after verification would invalidate every cached gate and force another full pass
4. Verify the final versioned tree — a release warrants the release posture from `../chill-vibe-full-regression/SKILL.md`:
   - after installing dependencies in a fresh worktree, verify `node_modules/electron/dist/electron.exe` exists. pnpm may report `Ignored build scripts: electron`; when the executable is missing, run `node node_modules/electron/install.js` before the release verifier. Otherwise the Node icon test and every Electron runtime test fail for environment setup rather than candidate code.
   - run `pnpm test:release` (`pnpm test:full` remains a compatibility alias). It runs legal inventory, quality, manifest-isolated Node tests, full Playwright, one combined Electron runtime/performance session, and the production build.
   - the verifier stores per-stage logs and evidence outside the repo, keyed by HEAD plus staged, unstaged, and untracked content. It only reuses a green stage when the exact fingerprint is unchanged; any source, test, version, or untracked-content change creates a new verification set.
   - **run long verification decoupled from the host session.** Launch via `Start-Process -WindowStyle Hidden cmd.exe '/d', '/s', '/c', 'pnpm test:release > <repo-external log> 2>&1 && echo ALL_GATES_GREEN >> <log> || echo GATE_FAILED >> <log>'`, then monitor the outer log plus the evidence directory printed near the top. If the driving CLI restarts, run `pnpm test:release` again: passed stages for the unchanged fingerprint are reused, while interrupted/running/failed stages run again.
   - `pnpm test:risk` is acceptable mid-iteration, but the final pre-tag gate for a real release is `test:release`
   - the verifier deliberately continues after a failed stage so one pass reveals the complete failure set. Do not manually restart unreached stages unless the verifier itself crashed before recording them.
   - use `pnpm test:release --stage <id>` only to retry an environmental failure on an unchanged tree. If code or test files changed, the fingerprint changes and the command remains non-green until every required stage passes for the new tree. A selected stage can show `PASS` yet the command still exit nonzero because another previously failed required stage remains unresolved; trust the per-stage summary/evidence for the retry result, not the wrapper exit code alone.
   - in a fresh isolated worktree, the first Electron stage can expose an artifact-creation race when several runtime files call `ensureElectronRuntimeBuild()` before `dist/client` and `dist/electron` exist. If the failures are only missing/rename/access errors inside those generated directories, let the verifier's production-build stage finish, then retry `pnpm test:release --stage electron` on the unchanged fingerprint; investigate or baseline-compare any failure that remains after the artifacts exist.
   - keep the Electron runtime harness on the repo Vite wrapper: launch `node scripts/run-vite.mjs ...`, not `node node_modules/vite/bin/vite.js ...`. The package entry can print `ready` and then exit because its dynamic import is not awaited, while the wrapper stays alive and still gives the harness a directly killable Node process. When this launcher changes, update the matching source assertion in `tests/electron-runtime.test.ts` in the same slice.
   - when the Electron Git stage performance gate fails after checkbox feedback already painted, do not assume a missing virtualized row means staging failed. Check the real index with `git diff --cached --name-only`, filter the dialog to mount the target row, and wait for each requested path to settle before classifying it as a product regression. Rapid optimistic clicks can otherwise race the proving assertion rather than the user-visible feedback.
   - use `pnpm test:release --plan` to inspect resume decisions and `pnpm test:release --fresh` only when matching cached evidence must be discarded intentionally.
   - Node tests run as separate registered files with bounded concurrency. Rerun one file with `pnpm test --files=<name>.test.ts`; the extra standalone `--` is parsed as an unknown argument by the repo runner. Do not boot the old all-imports entrypoint for focused triage.
   - **a Node failure that is red under the full manifest and green when the file runs alone is a concurrency-pressure artifact, not a verdict on the candidate — but it still has to be fixed, not waived.** Two shapes seen so far: a short `spawnSync`/`Promise.race` guard timing out (harden the margin to roughly 5× normal cold-start cost), and Windows `EBUSY: resource busy or locked, rmdir` inside a `t.after` temp-dir cleanup (v0.20.0: process exit and cwd-handle release are not simultaneous on Windows, worst of all for a git the test just killed — pass `{ maxRetries: 10, retryDelay: 100 }` to `fs.promises.rm` rather than sleeping a fixed amount). Suspect the candidate first when it added tests to that same file that spawn or kill children: more temp dirs and more kills raise the hit rate even though no assertion changed. Either way, rerun the new exact fingerprint.
   - importing the timestamped packager is side-effect free, so Node verification must not create a release directory or ZIP. The only happy-path package build remains the server-side `release-zip.yml` workflow.
   - after the final fingerprint is green, do not edit SPEC task checkboxes or write evidence back into the candidate tree. Keep verification evidence repo-external; any post-green tracked edit creates a new candidate and requires a new exact-tree pass.
   - if Playwright tooling noise from `AGENTS.md` blocks a clean run, capture the exact failure and continue with the strongest proven alternative only if the release is still honestly defensible
   - if the bundled Playwright browser is missing/corrupt and `playwright install` stalls, stop only the verified installer/downloader children, then run the same full suite through a repo-external temporary config pointed at the installed system Edge with `--workers=1`. Keep the candidate snapshot naming/template intact, rerun without `--update-snapshots`, and treat only intentional candidate UI diffs as snapshot updates; delete the temporary config afterward.
   - if a narrow failure looks pre-existing, prove that instead of guessing: reproduce the same test against `origin/main` in a repo-external detached comparison worktree, then remove it. Only classify the failure as baseline noise when the release candidate's affected/targeted gates pass and the baseline shows the same failure.
   - when a broad Playwright run mixes baseline snapshot drift with candidate-only snapshot changes, baseline-compare the failing spec first. For candidate-only diffs, inspect the actual/diff images in both themes and narrow layouts, update only the snapshots whose new rendering is intentional, then rerun those exact specs without `--update-snapshots`; never accept unrelated baseline drift along with them.
   - if fixed port `5173` is owned by an unrelated checkout, do not stop or reuse that process. Record the Playwright gate as port-blocked, then prove Electron runtime coverage against a free strict Vite port with the repo-local test environment. Do not run the stock `test:electron` while an unrelated service owns `5173`; its harness can validate the wrong renderer. On Windows, inspect the bind address too: an old `::1:5173` listener and an isolated candidate on `127.0.0.1:5173` can coexist, but only treat that as safe after proving both command lines and listeners.
   - if `5173` belongs to the primary checkout that supplied the candidate and the isolated release worktree was created only to avoid concurrent writes, a `PW_REUSE_SERVER=1 pnpm test:release --stage playwright` retry may use that server **only after** proving the candidate's complete renderer source/test delta against the primary checkout is already represented there. Otherwise treat it as unrelated and keep the gate port-blocked. Record the ownership proof; never silently reuse a server merely because both paths share a repository name.
   - when a standalone harness has printed its final green summary but its process stays alive, inspect the process tree and port `5173` before calling it hung. Stop only the verified test child, record the printed summary, and never touch a packaged Chill Vibe process. A full Node gate can also run far longer than its historical wall time when active Git cards leave many child processes behind; monitor the stage/log and process tree rather than killing the user's runtime.
5. Integrate into local `main`, push, prove convergence, tag, and **immediately create the release** (order is load-bearing):
   - write a concise release-oriented commit message and commit only the intended verified files. If the commit was created in a release worktree, record its branch and commit hash, then return to the primary checkout.
   - before publication, fetch `origin/main` again and require it to still equal the recorded remote base. If a release worktree was used, require local `main` to still equal its recorded local base; if the candidate was committed directly on local `main`, require `main` to equal the verified candidate commit. Also require the primary checkout to have no unmerged paths or unrelated dirty files. If an expected ref moved or the checkout cannot safely integrate, stop, reconcile, and rerun verification for the changed fingerprint.
   - advance the primary local branch first: when a release branch was used, run `git merge --ff-only release/v<version>` from the local `main` checkout. If fast-forward is impossible, do not bypass it with a direct refspec; reconcile the history deliberately and re-verify.
   - when the primary checkout contains the same uncommitted candidate that was verified and committed in the release worktree, compare the complete dirty path set and normalized file contents before cleaning the duplicate. Preserve a repo-external patch for tracked changes, then remember that `git reset --hard` does **not** remove duplicated untracked additions: remove only the individually verified untracked paths already secured in the release commit before the `--ff-only` merge. Never use a broad clean command here.
   - push only the local branch ref: `git push origin main`. **Never use `git push origin HEAD:main` from a release worktree or detached checkout.**
   - immediately run `git fetch origin main`, require `git rev-parse main` to equal `git rev-parse origin/main`, and require `git rev-list --left-right --count main...origin/main` to return `0 0`. In PowerShell, parse the two counts with `@((git rev-list --left-right --count main...origin/main).Trim() -split '\s+')`; do not compare against single-quoted `'0`t0'`, because PowerShell leaves the backtick literal there and can falsely block a converged release. A release is not publishable while the normal local workspace is ahead, behind, or diverged from the remote branch it just updated.
   - create the annotated tag from synchronized local `main`: `git tag -a v<version> -m "v<version>" main`. Require `git rev-parse v<version>^{}` to equal both branch hashes, then `git push origin v<version>`.
   - **immediately after the tag push:** `gh release create v<version> --verify-tag --title v<version> --notes <concise notes>`
   - Why immediately: the tag push already started `release-zip.yml`, and its "Remove stale in-progress zip assets" step does `gh api releases/tags/<tag>` — it hard-fails with HTTP 404 if no release exists yet (v0.17.8 and v0.17.11 both died here after 3+ min of server build). Recovery is cheap (`gh release create v<tag> --verify-tag --notes ...` then `gh run rerun <failed-run-id>`), but the right order avoids it entirely.
6. Let the workflow deliver the asset, then verify:
   - `gh run list --workflow release-zip.yml --limit 1 --json databaseId,status,conclusion` then `gh run watch <databaseId>` (expect ~3–4 minutes)
   - the workflow itself verifies `assets[].state == 'uploaded'` and that the download URL returns HTTP 200, so a green run IS the asset verification
   - confirm and record: `gh release view v<version> --json url,assets --jq '{url, assets: [.assets[] | {name, size, state}]}'`
   - 6b. Fallback, ONLY if the workflow failed or never produced the asset:
     - first try `gh workflow run release-zip.yml -f tag=v<version>` (server-side rebuild — preferred; it builds from the tag and self-verifies)
     - only if server-side is unusable: build locally with `pnpm electron:build:zip`, take the newest `dist/release-*` zip, upload with the call-operator form `& gh release upload v<version> $zip --clobber`, then re-verify the asset list yourself
7. Restart the active repo runtime before handoff:
   - follow `AGENTS.md`; prefer `pnpm dev:restart`
   - **skip the restart if the concurrency check (step 1) found another active agent** — never restart the shared dev runtime while another agent is working
   - remove any release worktree created in step 1 only after local `main`, `origin/main`, and the release tag have passed the equality checks and the release asset is verified
8. Retrospect and update this skill (mandatory, see Skill Self-Maintenance):
   - review the run you just did: where did reality diverge from this document? Which step was wasted, wrong, missing, or only survived thanks to improvisation?
   - apply the resulting edits to this SKILL.md before handoff — a release is not finished while the skill still describes a flow you did not actually follow

## Audit Rules

- Do not assume “no leak” because the diff looks code-like. Search for:
  - real secrets or keys
  - bearer tokens or auth headers
  - local machine paths such as `C:\Users\...` or `D:\...`
  - temp/debug leftovers (`console.log`, `debugger`, scratch docs, throwaway fixtures)
- **New user-visible copy must come from `shared/i18n.ts` with both a zh and an en value.** No gate catches a literal pasted into JSX: v0.20.2 shipped `<span>{text.automationBoardTitle}（实验性）</span>`, which renders "Automation Board（实验性）" in the English UI. Typecheck, lint, Node tests and every screenshot (taken in one language) stay green. Grep the diff for CJK characters inside `src/**/*.tsx` — outside `shared/i18n.ts` and code comments, a hit is almost always this bug.
- Expected test-only placeholders are acceptable when they are fake and obviously scoped to tests.
- Review deleted files too; make sure a deletion is intentional, not accidental.
- If unrelated files slipped in, unstage or revert them before the release commit.

## Verification Rules

- Prefer repo scripts over ad hoc commands.
- Use the release posture from `../chill-vibe-full-regression/SKILL.md`.
- If a verification command fails, do not publish anyway unless the failure is clearly a pre-existing harness issue and you can explain why the release remains safe.

## Versioning Rules

- Default bump: patch. Minor is reserved for a major stability milestone or a marker over many accumulated patches — never for feature volume (see Workflow step 3).
- Tag format: `v<package.json version>`.
- Keep the release title equal to the tag unless the user asked for a different naming scheme.
- Release notes can be concise and derived from the audited diff summary; do not paste huge raw diffs.

## GitHub Release Rules

- Server-side build via `release-zip.yml` is the canonical asset path; a green workflow run is the asset verification.
- Local `main`, `origin/main`, and the annotated release tag must resolve to the same commit before the release is created. Remote-only success is a failed release handoff.
- Confirm the release asset actually exists after the run; do not trust command success alone.
- In the final handoff, report:
  - commit hash
  - pushed branch
  - new version
  - tag
  - GitHub release URL
  - final downloadable asset URL (and local zip path only if the fallback was used)

## Skill Self-Maintenance

This skill maintains itself. Step 8 of the Workflow is not optional: every run ends with a retrospective edit pass over this file. History shows why — the "push tag → create release immediately" rule and the concurrency worktree rule both sat in the pitfall list for multiple releases while the main Workflow kept teaching the outdated local-build flow, and agents following the main flow re-hit the same failures.

Classify every lesson from the run before writing it down:

- **It changed how the release should be done** (a step order, a command, a decision rule) → edit the Workflow step itself. Never record a flow change only as a pitfall bullet; that is how the main flow drifts.
- **It was a one-off accident with a recovery trick** (a hang, a quoting bug, an environment failure) → add a bullet to Release Pitfalls / Fast Recovery.
- **A recorded pitfall no longer applies** (the main flow now prevents it, or the referenced tool/workflow changed) → delete it. Stale pitfalls are as harmful as missing ones.

Guardrails:

- Keep Release Pitfalls under roughly 10 bullets. Before adding a new one over that budget, merge or delete an old one first.
- Also check for silent drift even on a clean run: do the commands and file paths this skill references (`.github/workflows/release-zip.yml`, `package.json` scripts like `test:release` / `electron:build:zip`, `gh` invocations) still exist and behave as described? If the repo moved, move the skill.
- If the release commit/tag is already pushed, make the skill update a separate follow-up commit so the shipped tag stays immutable. Otherwise fold it into the release commit.
- Release-specific traps belong here, not only in `AGENTS.md`.

## Release Pitfalls / Fast Recovery

- **Four ways argument passing silently breaks before a single test runs. All of them look like the tool is broken.**
  - `powershell -File script.ps1 -Specs a,b,c` cannot pass an array — with `-File` every argument arrives as a literal string, so the comma form becomes ONE spec name (`No tests found`) and the space form spills into the next positional parameter (`-Mode` fails its `ValidateSet`). Write a two-line repo-external wrapper that calls it in-process — `Set-Location <repo>; & '.\scripts\run-playwright-specs.ps1' -Specs @('tests/a.spec.ts','tests/b.spec.ts')` — and launch **that** with `-File`.
  - `Start-Process -ArgumentList @('-File','x.ps1','-RedirectStandardOutput')` passes the redirect flag **to the script**, which then dies on an unknown parameter. Redirection is a `Start-Process` parameter, never an ArgumentList member.
  - Running `powershell -File D:\\Temp\\x.ps1` through the Bash tool eats the backslashes and yields `D:Tempx.ps1` (`-File` reports "not an actual argument"). Launch PowerShell scripts through the PowerShell tool, not through Bash.
  - Uploading a path containing spaces via `Start-Process -ArgumentList @(..., $zip, ...)` joins the array into one string and lets `gh release upload` split `Chill Vibe-...zip` at the space — use the call operator, `& gh release upload v<tag> $zip --clobber`. Generating curl config lines: wrap concatenated strings in parentheses, `('output = "' + $path + '"')`, or PowerShell spreads the value across lines.
- A smoke script can be a **false-positive machine**, and then it is worse than having none: it converts "unverified" into "verified" at zero cost. `smoke-packaged-backend-isolation.ps1` matched four ready strings of which three did not exist anywhere in the source, and the fourth (`Resource heartbeat`) is written by `initCrashLogger()` — which runs *before* `ensureBackend()` and touches nothing the backend owns. It would have printed "冒烟通过" with the backend entry missing from the asar entirely. Rule for any smoke: **the ready criterion must be a signal only the target path can produce** (here, a child process whose command line matches `node.mojom.NodeService`), and you must observe it both green and red before trusting it. Grepping that the criterion string even exists in the source is the 10-second version of this check.
- `gh release create` can time out after partially creating a draft or empty release. After any timeout, do not rerun blindly:
  - stop orphaned `gh.exe` create/upload processes first, then inspect `gh release view v<tag> --json apiUrl,uploadUrl,url,assets,isDraft,isPrerelease,tagName,publishedAt`;
  - if the release exists but has no asset, keep it and let the workflow (or a `workflow_dispatch` rerun) upload the asset;
  - if it is an accidental draft with an `untagged-*` URL, verify whether it still exists through the API/list view before deleting or recreating.
- If a manual `gh release upload` (fallback path only) hangs on the large zip while a tiny probe asset uploads successfully, prefer `gh workflow run release-zip.yml -f tag=v<tag>` so GitHub builds/uploads/verifies server-side. Use a manual `curl.exe --http1.1` upload against the release `uploadUrl` only as a last resort; put the token only in a temporary curl config, never echo it to logs, and delete probe assets immediately after the check.
- **A detached gate that looks frozen usually isn't — the log is buffered, so read the process, not the file.** v0.20.5's `eslint .` showed no log output for 12 minutes and the log's mtime never moved; the stage had in fact finished in 91.7 s and the writes were still sitting in the pipe. Before concluding a hang, sample the actual worker's CPU twice (`(Get-Process -Id $pid).CPU`): rising = working, flat = stuck. The same buffering makes wall-clock estimates from the log useless — check the clock, not your sense of elapsed time.
- **The full Playwright stage has genuine 14-worker flake, and `--stage playwright` on an unchanged tree is the sanctioned way to settle it.** v0.20.5 lost one hover-timing assertion (`composer hover recovers ... in light theme`, a `.poll(:hover)` predicate) in a run where the same test's dark-theme twin passed and the identical code had gone 467/467 minutes earlier. Prove it rather than assume: the retry ran green (467 passed) and the whole gate flipped to ALL GREEN. Only treat a Playwright red as flake when the code path is untouched by the candidate AND a retry on the byte-identical tree passes; a red that reproduces is a real break.
- Do not keep retrying the full regression wrapper when it is blocked by known fixed-port `5173` ownership or a flaky Playwright check. Capture the exact wrapper failure, prove whether a same-candidate primary-checkout server is reusable under Workflow step 4, and rerun the failing spec or strongest targeted gate in isolation; stop only a verified repo-local test server, never an active shared dev or packaged runtime. If the same focused failure reproduces unchanged against `origin/main`, record it as baseline harness/product noise only after the candidate's affected gates pass; do not silently turn an unproven red stage green.
- Baseline-comparison worktrees: create them OUTSIDE the repo (e.g. `D:\Temp\...`) — one under `.claude/worktrees/` can stay locked by zombie test processes and resist even `Remove-Item -Recurse -Force` (v0.18.1 left an undeletable shell). They may intentionally share `node_modules` through a junction, so do not run `pnpm install` there when pnpm says it will remove the shared modules directory; use the linked dependencies or make a fresh isolated worktree. To delete: `[System.IO.Directory]::Delete($junction)` first, then the files; leave an empty handle-locked shell for the next reboot.
- If the full Playwright suite cannot launch because the bundled browser is missing/corrupt, or Chromium reports `FATAL ... Failed to start BrowserThread:IO`, treat the cascade as a local browser harness/resource failure. Stop only the verified installer/downloader or orphaned `ms-playwright` children, verify `5173` is free, then use Workflow step 4's temporary system-Edge full-suite fallback (or the strongest practical targeted gates when even Edge is unusable) instead of blindly looping the stock suite.
- If `pnpm test:risk` fails with `ENOSPC` while tests copy `node.exe` into `%TEMP%`, move `TEMP`/`TMP` to a repo-external drive with free space (for example `D:\Temp\chill-vibe-release-temp`) before rerunning. Do not point temp at a directory inside this repo: fake CLI `.js` files then inherit the repo `"type": "module"` package scope and fail with `require is not defined`.
- Avoid piping release verification commands through `Tee-Object` when their harness launches Vite, Electron, or other background children. A detached child can inherit the pipe, or a repo-local Vite child can survive harness cleanup, after the tests have already printed a green summary; inspect the log/process tree, stop only the verified test child, and use the printed summary instead of waiting forever for a wrapper marker. When detaching with `Start-Process`, generate each `.cmd` line as one interpolated string; PowerShell array concatenation can split quoted paths across lines and make the wrapper exit before creating its log.
- Clean up release scratch files before final handoff (`.tmp-release-notes-*`, `.tmp-gh-upload-*`, `.tmp-curl-*`) unless they are intentionally needed for audit evidence.
- If repeated `gh run watch` calls are cut off by a short host command timeout, poll `gh run view <id> --json status,conclusion,jobs,url` instead; this keeps the server-side build authoritative without restarting or duplicating it.
