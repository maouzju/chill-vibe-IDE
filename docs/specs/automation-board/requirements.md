# 自动化看板 (Automation Board) — Requirements

## Problem

Chill Vibe 目前一个需求 = 一个 tab。用户要并行推进十几个需求时，只能开十几个 tab 手动逐个发起、逐个盯、逐个催。缺三样东西：

1. **批量编排**：一个可视化的需求队列，能一眼看到"哪些排着、哪些在跑、哪些完了"。
2. **无缝升降级**：看板上的小卡片和完整聊天窗口必须是**同一个 agent 会话的两种展现**，用户想介入就把它拖出来，介入完再塞回去，中间不能有任何"重新开始"。
3. **自主监工**：最后一个需求跑完时，能自动唤起一个有看板视野和操作权限的 AI，替用户做"检查交付 / 决定鞭策还是归档"这层判断。

> **v2 修订（2026-08-11）：监工不再是一个特殊实体。**
> v1 把监工做成了"内置在看板里的一张特殊卡片"（`board.supervisorCardId`）+ "工作区唯一一套自动触发配置"（`autoTrigger`），于是系统里同时存在两套并行概念：模板/需求项是一套，监工是另一套。v2 把它们合成一套：
>
> - **监工 = 一个默认存在的模板**（`builtIn: true`），没有任何特殊代码路径。
> - **触发器下沉到模板**：任意模板都能配触发器，到点了就等于"自动帮你把这个模板拖进泳道"。
> - **"能操作别的会话"变成一个卡片级权限开关：超管权限**（`adminAccess`）。任何会话都能开，开了就拿到工作区 MCP。监工模板只是默认勾了这个开关。
>
> 下文 FR6 / FR7 / FR10 已按 v2 重写；FR1–FR5、FR8、FR9 不变。

## Users & Scope

单机桌面用户（本仓库唯一用户形态）。一个工作区（project）对应一个自动化看板。看板是一种**卡片类型**（像 Git / Files / Brainstorm 一样从空态工具栅格或模型选择器创建），寄居在工作区列的某个 pane tab 里。

## Functional Requirements

### FR1 — 看板结构

- 卡片类型标识 `__automationboard_tool__`，一个工作区列里同时可以有多张（不做单例限制，但默认只创建一张）。
- 三条固定泳道（lane），顺序固定：`待命 standby` → `执行中 running` → `已完成 done`。
- 每条泳道承载任意数量的**需求项 (board item)**，项内有序，顺序由用户拖拽决定。
- 泳道标题旁显示该道的项数。

### FR2 — 需求项就是 agent 会话

- 一个需求项**就是一张真正的 `ChatCard`**，与普通聊天 tab 的卡片同型、同源、同执行路径。它存在于工作区列的 `column.cards` 里，只是不出现在任何 pane 的 `tabs` 数组中。
- 新建需求项：在 `待命` 道底部输入需求文本 → 创建卡片，需求文本进入卡片 `draft`，不发送。
- 项被移入 `执行中` 时**立即发起一次发送**，走与"普通 tab 里敲字回车"完全相同的路径（`sendMessage`），不走任何捷径。
  - 若该卡已有会话历史（曾经跑过、被拖回待命又拖回来），则发一次**空续传**而不是重复原需求，语义是"继续"。
  - 若是首次执行，发送 `draft` 里的需求原文，`draft` 随之清空（与真实 composer 行为一致）。
- 项被移入 `待命` 时**立即中断**当前运行（等价用户点停止），保留会话与上下文，不清空队列语义上属于"暂停"。
- 项被移入 `已完成` 时中断运行（如果还在跑），并停止一切自动化（唤醒、循环、监工不再管它）。

### FR3 — 紧凑展现

- 项卡片高宽受限（默认宽度撑满泳道、高度上限约 220px），只渲染**最近若干条** agent 消息（默认末 6 条可渲染条目），超出部分不渲染，不做虚拟滚动。
- 项卡片的边框与状态色**沿用现有 agent 聊天卡的视觉语言**（idle / streaming / failed 三态边框），不新造一套配色。
- 项卡片头部显示：需求标题（取自卡片 title，缺省用需求首行）、provider/model 胶囊、状态点、操作按钮（停止 / 拖出 / 更多）。

### FR4 — 双向拖拽（核心）

| 拖动 | 落到 | 结果 |
|---|---|---|
| 看板需求项 | 本列任意 pane 的 tab 栏 | 该卡片成为一个真正的 tab（插入到落点位置），从看板泳道移除。**会话、消息、sessionId、streamId、正在跑的流全部原样保留**，只是展现方式变了。 |
| 看板需求项 | 本列 pane 内容区边缘 | 同上，但顺带分屏（复用现有 split 落点逻辑）。 |
| 已有 chat tab | 看板 `待命` 道 | 该卡片从 pane tabs 移除、进入待命道，**并立即中断**其正在进行的运行。 |
| 已有 chat tab | 看板 `执行中` 道 | 同上但**立即执行**（有历史则空续传，无历史则发 draft）。 |
| 已有 chat tab | 看板 `已完成` 道 | 移入并中断，不再自动化。 |
| 看板需求项 | 另一条泳道 / 同道另一位置 | 按 FR2 的进出语义处理（中断/执行），同道内仅重排不触发执行。 |
| 模板 | `待命` / `执行中` / `已完成` | 由模板实例化一张新卡片进入该道，落 `执行中` 立即执行。 |

约束：

- 跨工作区列拖拽**不支持**（看板的项必须与看板同列，因为 workspacePath 决定 agent 的 cwd）。落到别列的看板时拒绝并不显示落点提示。
- 拖出到 tab 栏后，若该卡正在 streaming，流必须继续，不得断连、不得重发。
- 每一次搬运都必须是**原子的**：两端（源容器、目标容器）先一次性校验，任一端失效则整体不动（AGENTS.md pitfall 237）。
- 停流与队列处置必须成对决策，不得散落在调用点（pitfall 246）。

### FR5 — 计划唤醒与循环重复

- 执行中的项支持现有的 `计划唤醒`（wakeTimer*）与 `循环重复`（repeatLoop*），字段与行为完全复用卡片级现有实现。
- 唯一差异是 UI 与语义方位：`left-tab` 模式在普通 tab 里叫"左侧 tab"，在看板项上叫**"上方需求"**——即同泳道内它上面那一项。
- 唤醒目标序列在看板语境下 = 该项所在泳道的有序项 id 列表（普通 tab 语境下 = pane.tabs）。判定函数不变。

### FR6 — 模板（v2）

- 任一项可"保存为模板"，保存需求文本 + provider + model + reasoningEffort + thinkingEnabled + planMode + 唤醒/循环设置 + **超管权限**。
- 模板**按工作区持久化**，与看板卡片的生命周期解耦（删掉看板 tab 不丢模板）。
- 看板底部显示模板条（横向），每个模板可拖入任一泳道，也可点击重命名 / 编辑 / 删除。
- 每个模板可展开一个**配置面板**，可改：名称、需求文本、provider/model、超管权限、触发器（见 FR7）。
- **默认模板**：新工作区自动带一个 `builtIn: true` 的 `看板监工` 模板 —— 需求文本是原监工文案、provider `claude`、`adminAccess: true`、触发器 `last-item-settled` 但**默认关闭**（用户自己去打开）。
  - 内置模板可以被编辑，也可以被删除；删除后该工作区就没有监工，这是允许的。
  - 内置模板提供"恢复默认文案"按钮。

### FR7 — 模板触发器（v2，取代原"自动触发/监工"）

- 触发器是**模板的一个字段**，不再是工作区的全局配置。每个模板独立开关、独立节流。
- 触发条件（v2 仍只有一种，结构留扩展）：`last-item-settled` —— 看板上最后一个处于 `执行中` 且真正在跑的项结束（AI 收尾、含原生后台等待结束）时触发。
- 触发动作 = **自动执行一次"把这个模板拖进目标泳道"**（默认 `执行中`），与用户手动拖模板走完全同一条代码路径。这就是 v2 的一致化：触发器不引入任何新的执行语义。
- **实例复用**：模板记住上一次由它触发生成的卡片 `instanceCardId`。
  - 那张卡还在本看板里 → 复用它（把它挪回目标泳道并发一次需求文本），于是监工像 v1 一样保有跨轮上下文。
  - 那张卡已被删除 / 拖出看板 → 新建一张，`instanceCardId` 更新。
- 每个看板项记录 `templateId`（由哪个模板实例化而来，手动新建的项为空）。
- 防抖与防递归（全部改为按模板判定）：
  1. 触发器关闭 → 不触发。
  2. 结束的那张卡不是本看板 `执行中` 道的项 → 不触发。
  3. 结束的那张卡的 `templateId` 就是本模板 → 不触发（**这是防自触发的核心**：监工自己跑完不会把自己再叫起来）。
  4. `执行中` 道里还有别的卡在跑（含本模板的实例） → 不触发。
  5. 距上次本模板触发不足 `minIntervalMinutes` → 不触发。
- 触发出来的实例卡的 cwd 是本工作区，因此天然带项目上下文。

### FR10 — 超管权限（v2 新增）

- **任何** Chill Vibe 会话卡片都有一个"超管权限"开关（`card.adminAccess`），位置在 composer 的设置菜单里，与思考深度 / 计划模式 / 自动鞭策并列。
- 开启后，该卡片的**每一次请求**都会把工作区 MCP 接进 provider 启动，让这个会话能读写**同一个工作区列里的其他会话**：
  - 读：列出本工作区所有会话（标题、provider/model、状态、静默多久、最近转录）。
  - 写：向某个会话发消息（=鞭策）、把某个会话移进看板的某条泳道、给某个会话挂计划唤醒。
- 关闭时**完全拿不到**这些工具 —— 这是权限边界，不只是优化。默认关闭。
- 开启的卡片在 UI 上必须有明显标识（composer 开关高亮 + 卡片头部一个盾牌角标），因为它能改别的会话。
- 作用域严格限制在**本工作区列**：拿不到别的列的会话，也拿不到任意文件/命令权限（那由该卡片自身的 provider 沙箱决定，与本开关无关）。
- 写操作一律转发给渲染进程复用电脑端 handler，桥接服务自身绝不改 state（与手机远程监工同一条规矩）。

### FR8 — 看板 tab 的运行态

- 承载看板的那个 pane tab，当且仅当看板上**存在至少一个真正在运行的项**时显示橙色运行态（与普通 streaming tab 同款 `is-streaming`）。v2 起监工实例本身就是 `执行中` 道的一个项，所以不再需要单独判监工。
- 该状态是**派生**的，不得靠把看板卡片的 `status` 写成 `'streaming'` 来伪造（会污染重启恢复路径，pitfall 113）。

### FR9 — 持久化与升级

- 所有新增持久化字段必须有 Zod schema + 默认值 + 归一化路径，旧存档加载不得报错、不得丢字段（pitfall 5/6）。
- 看板项卡片与普通卡片在磁盘上无区别，因此现有的消息裁剪、structuredData 压缩、sidecar 归档全部自动生效。
- 重启后：在跑的项卡片走现有 `attachStreamsForState` 重连（它遍历 `getOrderedColumnCards`，已覆盖不在 layout 里的卡片）。

## Non-Functional Requirements

- **NFR1 性能**：看板可能同时挂 10+ 个 streaming 项。项卡片的状态指示**不得引入无界 paint 动画**（pitfall 218/216）；紧凑消息渲染必须是有界条数，不得对全量 messages 做 markdown 解析。
- **NFR2 单一 lane**：所有 reducer 提交保持 urgent lane，禁止 `startTransition` 包 `applyAction`（pitfall 194）。
- **NFR3 双主题**：所有新表面在 light/dark 下都要正确，token 走 `src/index.css` 现有变量（pitfall 4）。
- **NFR4 可测**：编排/判定逻辑必须抽成模块级纯函数并对真实调用顺序断言，不得用 `readFileSync` + 正则做源码文本快照（pitfall 248）。
- **NFR5 MCP 安全**：看板 MCP 只暴露看板域的操作，不给任意文件/命令权限；写操作必须走 App.tsx 的真实 handler，不得另开捷径（remote-monitor 已定的规矩）。

## Out of Scope (v1)

- 跨工作区看板 / 全局看板。
- 泳道自定义（增删改名、多于三道）。
- 看板项之间的依赖图（DAG）。
- 触发条件除 `last-item-settled` 之外的类型（结构留好，UI 只出一种）。
- 看板项的批量选择操作。

## Acceptance Criteria

1. 从空态工具栅格能创建"自动化看板"卡片，tab 有专属图标与标题。
2. 在待命道输入需求 → 出现项卡片，未发送。
3. 把它拖到执行中 → 立刻开始跑，项卡片内出现流式输出，看板 tab 变橙。
4. 把这个正在跑的项拖到 tab 栏 → 变成一个真 tab，**输出不中断**、`sessionId` 不变、消息不丢。
5. 在那个 tab 里追问一句 → 正常回答。把 tab 拖回执行中道 → 继续留在执行中且不重发原需求。
6. 把 tab 拖到待命道 → 立即中断，状态回 idle，会话保留。
7. 给执行中的项开计划唤醒，模式选"上方需求"，UI 文案是"上方"，行为是等同泳道上一项结束。
8. 项存为模板 → 底部出现模板 → 拖进执行中 → 新项立即开跑；删掉看板 tab 再新建看板，模板仍在。
9. 新工作区的看板底部默认就有一个 `看板监工` 模板；展开它的配置面板能改需求文本、模型、超管权限、触发器开关与间隔，重启应用后配置仍在。
10. 打开 `看板监工` 模板的触发器 → 让唯一在跑的项结束 → 监工实例作为一个**普通看板项**出现在执行中道并开跑；它能通过 MCP 列出工作区会话、把某个会话移到已完成、向某个会话发一条鞭策消息，界面上真实生效。
11. 监工实例跑完**不会**把自己再次触发（`templateId` 自触发防护）；第二次触发复用同一张实例卡，上下文延续。
12. 在一个**普通聊天 tab**（不在看板里）的 composer 设置菜单里打开"超管权限"，该会话同样能列出并操作本工作区的其他会话；关掉后工具消失。
13. `pnpm test:quality` 绿；新增 Node 测试绿；`pnpm electron:build` 出包。
