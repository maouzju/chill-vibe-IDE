# 后端进程隔离 — 需求

## 背景：为什么这不是一次性能优化

用户长期报告两件事，一直被当成两个 bug 查：

1. **"用久了就卡死"** —— 窗口冻结数秒到十几秒
2. **"闪退"** —— 应用突然消失

2026-08-12 定案：**它们是同一件事**。当次闪退实例的退出码是 `0xCFFFFFFF`，由 WerFault 打上，
含义是「窗口 5 秒没有服务消息队列，Windows 把它当无响应程序杀了」。卡得短是卡顿，卡过 5 秒就是闪退。

外部监控实测（`logs/app-unresponsive.log`）：冻结 10797 / 19089 / 11303 / 14971 / 14472 ms，
期间主进程 **CPU = 0%**、主线程处于内核 Wait —— 不是在算，是被同步操作占住。

## 根因是结构性的

`server/`（60 文件 / 28385 行）全部跑在 Electron **主进程主线程**上，和窗口消息泵共用同一个线程。
于是后端任何一次同步/阻塞操作都直接冻结窗口。

其中最致命的是子进程创建：**libuv 在 Windows 上同步执行 `CreateProcessW`**，所以每一次
`spawn('git', …)` 都是主线程硬阻塞。2026-08-12 在用户机器上实测 40 次 git spawn：
p50 = 102ms，p90 = 1831ms，**最坏单次 6910ms** —— 一次就足以跨过 5 秒线。而 `diffWorkspaceSnapshot`
每轮对话结束跑一次，每个变更文件最多派生 3 个 git 子进程，文件上限 256。

**为什么削减调用点不算修好**：把最重的几处优化掉只是堵住当前的出血点，"消息泵和业务逻辑共用一个
线程"这个结构没有变。下一个重活（新功能、更大的 state、更多的会话历史）会重新把它撑破。这也是
这个问题反复"修好了又出现"的原因。

## 目标

把后端从主线程移走，使**主进程主线程上不再存在任何可能长时间阻塞的业务逻辑**。

已实测的可行性依据（`scripts/bench-main-thread-isolation`，2026-08-12）：同一批 20 次 git 调用，

| 跑在哪 | 单次最长停摆 | 停摆 >1s | 停摆 >5s |
|---|---|---|---|
| 主进程（现状） | 6827ms | 11 次 | 2 次 |
| utilityProcess | **58ms** | **0** | **0** |

## 需求

### R1 — 后端整体运行在独立进程
`electron/backend.ts` 与其依赖的整个 `server/` 树运行在 Electron `utilityProcess` 中，
不再与窗口消息泵共享线程。

**验收**：后端执行一批已知会阻塞的操作（≥20 次 git spawn）期间，主进程事件循环单次最长停摆
**< 500ms**，且无一次 ≥ 5000ms。用 `scripts/bench-main-thread-isolation` 的口径测量。

### R2 — 主进程侧改动最小化
`electron/main.ts` 的 108 个 IPC handler **不逐个改写**。通过一个与
`createDesktopBackend()` 返回值同形状的代理对象转发调用，使 handler 代码保持原样。

**验收**：main.ts 中 handler 主体的 diff 行数接近 0；替换点集中在 backend 的创建处。

### R3 — 行为完全等价
所有 108 个 IPC 通道的入参、返回值、错误传播语义与改造前一致。后端抛出的错误必须仍以拒绝
（rejection）形式到达渲染进程，错误信息不得丢失。

**验收**：现有测试全绿；错误传播有针对性测试覆盖。

### R4 — 推送型通道不退化
后端 → 渲染进程的主动推送必须继续工作，且不因跨进程而丢事件或乱序：
- 聊天流式事件（高频，热路径）
- Claude keepalive 的非请求流通知（`onUnsolicitedStream`）
- 手机远程监工写命令（`dispatchRemoteCommand`）
- 超管看板命令（`dispatchWorkspaceAdminCommand`）

**验收**：流式输出端到端可用；顺序保持；每类推送有测试覆盖。

### R5 — 后端进程崩溃可恢复
后端进程意外退出时，主进程必须能感知并恢复（重启后端或明确告知用户），**不得**表现为窗口
静默失效或所有操作永久挂起。

**验收**：杀掉后端进程后，应用不进入永久无响应状态。

### R6 — 打包后可用
utilityProcess 入口脚本必须进入 asar 并能在打包版中正确解析路径。

**验收**：打包产物实机启动，后端功能正常（不只是开发模式可用）。

### R7 — 数据目录与单实例语义不变
后端在独立进程中解析出的数据目录必须与改造前一致，不得出现"新进程另开一份 profile"。
`CHILL_VIBE_DATA_DIR` 等既有覆盖开关行为不变。

**验收**：改造后启动，读写的仍是原数据目录；打包版实机确认。

## 非目标

- 不重写 `server/` 内部实现，不做业务逻辑变更
- 不在本次解决 9195 个会话历史 sidecar / 1.1GB 数据目录的体积问题（另立）
- 不追求把主进程剩余的 Electron 侧工作也并行化

## 风险

| 风险 | 说明 |
|---|---|
| 结构化克隆边界 | 跨进程载荷必须可克隆；函数、类实例、循环引用会在运行时才炸 |
| 高频流式事件的开销 | 流式事件从函数调用变成跨进程消息，需确认不引入新的延迟或背压问题 |
| 初始化顺序 | 后端启动是异步的，早于它就绪的 IPC 调用必须排队而不是失败 |
| 回归面广 | 108 个通道全部改变传输方式，属于一次性大面积变更 |
