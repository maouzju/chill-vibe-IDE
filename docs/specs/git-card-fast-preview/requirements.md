# Git 卡牌快显加载需求

## 背景

Git 卡牌打开时会先等待完整 `inspectGitWorkspace()` 返回。完整状态会读取 diff 预览、最近提交和仓库描述；在改动多、文件大或磁盘较慢时，卡牌只显示“正在加载本地改动”，用户需要等到全部加载完成才看到「提交新增」「分析改动」「古法 Git」。

用户反馈：即使完整明细还没加载完，应用也应该已经能知道大概有多少改动，并尽早给出这几个操作入口。

## 目标

1. Git 卡牌首次打开时必须优先获取轻量状态：仓库是否存在、分支、ahead/behind、改动文件列表和数量。
2. 轻量状态可用后，即使完整 diff/最近提交仍在加载，卡牌也要展示改动数量和主要操作按钮：提交新增、分析改动、古法 Git。
3. 操作必须安全：点击提交新增、分析改动、古法 Git 时应基于最新可用状态继续执行；必要时由现有流程再拉取完整状态。
4. 完整状态加载完成后，文件列表和统计要自然升级，不闪成空状态，不隐藏已显示的按钮。
5. 非 Git 仓库、无工作区、错误态保持现有引导和刷新能力。
6. 轻量状态不能包含大 patch 文本，避免把慢加载和大 payload 提前搬到首屏。
7. 完整状态补齐多个已跟踪文件的 diff 时，不能为每个文件分别启动 `cat-file` 和
   `diff --no-index` 进程；普通多文件工作区应使用有界数量的 Git 进程批量生成预览，
   同时保留现有单文件、总量和 patch 大小上限。
8. 工作区干净时，只要仓库已配置 upstream，Git 卡片仍必须显示「同步」入口；本地无改动不代表远端没有新提交可拉取。

## 2026-08-10 主线程卡顿与状态保真补强

9. 已经加载过状态的 Git 卡片在聚焦或 tab 激活时，自动刷新必须走轻量 preview；自动刷新需共享节流窗口并禁止并发请求，鼠标掠过卡片不得触发刷新。
10. preview 刷新更新状态位时，不能清空屏幕上仍可用的 patch 与增删行统计；分析改动和完整 Git 面板等 patch 消费方必须在开工前确认拿到的是当前 workspace 的全量状态，必要时重新抓取。
11. Git 子进程的 stdout/stderr 按完整字节流解码，UTF-8 多字节字符跨 chunk 边界时不得产生替换字符。
12. 多文件 patch 按 block 建立一次索引，查找结果必须与原有线性匹配语义一致，同时避免随改动数平方增长。

## 非目标

- 不重做完整 Git 界面。
- 不引入后台常驻 watcher。
- 不改变提交、暂存、同步的语义。
- 不要求在轻量状态中提供准确增删行数；没有 patch 前可显示 `+0 / -0` 或弱化统计。
- 不把完整 Git 面板改成新的按需 diff 协议；本切片只消除现有完整状态路径的进程放大。

## 验证

- 后端单元测试覆盖轻量状态不带 patch 且符合共享 schema。
- 前端/桥接测试覆盖新 API 能从 Electron bridge 获取并校验。
- Git 卡牌行为测试覆盖：完整状态延迟时，轻量状态到达后按钮和改动数已可见。
