# 多窗口流式性能兜底 — 需求

## 目标

在不改变会话语义、不丢消息、不破坏输入焦点、滚动、恢复和持久化的前提下，让重度门禁中的 20 个长任务同时运行时，Chill Vibe 仍可稳定输入、点击、切换标签和滚动，并避免进入 `BrowserWindow unresponsive`。

本计划不承诺用一次大改“彻底优化”所有性能问题，而是要求每个切片都可证明、可回滚，并且上一切片验证完成后才能进入下一切片。

## 安全契约

- 完整消息、结构化活动、Provider 原生会话和持久化内容不得因 UI 性能兜底而删除、截断、重排或漏写。
- 不得恢复给 reducer 流式提交套 `startTransition` 的旧做法；该做法曾导致活跃 pane 被 React 删除重建和焦点丢失。
- 流结束、停止、报错、恢复、切卡、退出应用前，仍必须无损 flush 对应缓冲区。
- 输入框焦点、中文输入、选区、草稿、附件、Ask User、排队发送、手动停止和恢复流程不得退化。
- 性能兜底只改变“何时刷新”和“当前挂载多少 UI”，不改变 Provider 收到的上下文。
- 单条助手正文仍在流式增长且超过安全阈值时，允许暂时按原文渲染以避免每个 delta 重跑整段 Markdown；流结束后必须恢复完整 Markdown，状态和保存内容不得截断。
- 每个行为变化必须有独立开关或清晰回滚点；出现数据或交互回归时立即回滚当前切片，不叠加下一项修改。
- 多窗性能兜底不得限制 provider 并发数量；十几个会话应继续立即运行。任何资源修复都必须针对已证明的额外开销，而不是用排队降低并行能力。
- 逐 delta 执行的 Markdown/正文预处理必须对未闭合语法保持有界、近似线性；Provider 正在输出链接、代码或强调标记的中间态不得触发正则指数回溯或同步阻塞 renderer。

## 验收标准

### 确定性压力场景

建立隐藏窗口 Electron 压力夹具，至少覆盖：

- 20 个同时处于 `streaming` 的 Codex 卡片，分布在 6 个 workspace column、每 pane 14 个 tab 中；
- 总计约 1000 条消息、900 条以上结构化活动；
- 至少两个当前流式工具组各有 300 条以上 command/tool item；
- 按生产节奏持续注入 delta 和 activity；
- 压力期间循环执行输入、中文文本插入、点击聚焦、向运行中的 Agent 延后发送消息、滚动、切换 pane tab、展开/折叠和显示更早活动。
- 20 条流运行期间至少重复 60 次真实鼠标新建 Agent tab、立即输入中文、切走切回核对草稿并清理新 tab，覆盖复杂面板下偶发的新建后数秒无响应。
- 合成压力状态序列化后至少为 4MB，以覆盖长期历史状态下的创建与持久化成本，不读取用户真实消息。
- Provider 由本地 fake CLI 模拟，不联网、不调用真实模型、不消耗模型 Token；应用 Electron、路由、状态、渲染和持久化路径保持真实。

### 响应性

- 压力测试期间 `BrowserWindow unresponsive` 和 `render-process-gone` 次数均为 0。
- 主线程不得出现 2 秒以上无心跳；目标最大 stall 小于 500ms。
- 输入到 textarea 值更新的 p95 小于 100ms，点击到聚焦的 p95 小于 150ms。
- 运行中消息进入延后发送队列并绘制反馈的 p95 小于 500ms。
- 新建 tab 到 composer 聚焦的 p95 与 max 均小于 500ms；首次中文输入 p95 小于 250ms、max 小于 500ms，焦点失败次数为 0。
- 切换 tab、滚动和展开活动不得超时或需要重复操作。
- 5 分钟自动化压力测试通过后，发布候选包还需完成 30 分钟本机隐藏窗口 soak。

### 数据正确性

- 压力前后每张卡的消息 ID、顺序、数量和结构化数据一致；仅允许预期中的新增流消息。
- 当前 UI 隐藏的活动在 Provider 上下文、保存状态和恢复状态中仍完整存在。
- 流完成、手动停止、恢复、应用关闭时不会遗留未 flush 的 delta/activity。
- 交错的多个 assistant item 继续按 `messageId` 独立合并，不串消息、不覆盖。
- 同一条流消息因重连或事件重放被再次提交时，按消息 ID 幂等处理，不在内存或持久化状态中产生重复消息。
- 重新加载后，排队发送、草稿、附件、sessionId、streamId 恢复语义保持不变。
- 同步启动十几个会话时，每条流都进入 provider 启动路径，不出现后端并发排队。
- 重度日常形态必须覆盖多个 workspace window 同时存在，且单个 pane 的 tab 条达到十几个；不能只用 6 张各占一列的前台卡代表该场景。

### 交互与视觉

- 活跃流式工具组默认只挂载有界尾部，但标题显示完整总数。
- 显示更早活动按有界批次进行；新活动到达后最新项始终可见。
- 折叠组保持 header-only；普通短会话不出现无意义的性能提示。
- light/dark、桌面和窄视口都不引入新的布局跳动、焦点样式或滚动锚点变化。

## 非目标

- 第一阶段不改 Provider 协议、不自动执行 `/compact`、不改持久化 schema。
- Windows 不得继续无条件关闭硬件加速；必须保留 `CHILL_VIBE_DISABLE_HARDWARE_ACCELERATION=1` 作为兼容性回退。
- 不在缺少压力测试证据时引入整页虚拟列表、全局状态库迁移或 React 架构重写。
- 不为了跑分降低消息完整性、隐藏错误或降低恢复可靠性。

## 2026-07-23 长时运行状态动画兜底

- 长时间运行的 Provider 状态提示在当前可见 pane 中必须保留清晰动效；隐藏 pane 的状态点不得继续无限循环动画。
- 该约束覆盖流式回复点和命令运行点：前台提供即时反馈，后台使用静态层级，避免大量已挂载但不可见的 pane 持续占用合成预算。通用 busy 点继续保持静态。
- 验收必须包含真实可绘制 Electron 窗口的多流长时验证，并以零 `BrowserWindow unresponsive`、零 renderer gone 为硬门槛；空 JS 调用栈不能被当作无故障。

## 2026-07-25 持续无响应自动恢复兜底

- Electron 已确认窗口持续无响应、且在短暂宽限期内没有收到 `responsive` 时，应自动重新加载 renderer，避免用户只能强制关闭整个 IDE。
- 自动恢复只重建 UI renderer，不结束本地后端与 Provider 子进程；重新加载后继续依赖现有 stream backlog 重放和消息 ID 幂等合并恢复正在运行的会话。
- 短暂卡顿恢复、窗口已关闭或恢复功能被环境变量关闭时不得触发重新加载。
- 默认宽限期必须足够避开普通瞬时长帧，同时显著短于用户人工判定“彻底卡死”并关闭应用的时间；必须提供环境变量关闭或调整。
- 每次自动恢复必须写入主进程日志，包含窗口、renderer PID、无响应持续时间和最后输入摘要，便于继续定位底层 GPU/合成链路根因。
- 自动恢复必须实际替换卡死的 renderer 进程；仅对仍卡住的同一 PID 调用普通 reload 不算恢复成功。主进程日志和 Electron 运行时测试必须证明恢复前后 renderer PID 不同且 UI 已重新挂载。
