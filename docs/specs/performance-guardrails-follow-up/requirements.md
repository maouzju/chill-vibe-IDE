# 性能门禁补强与大 Diff 预览减负 — 需求

## 背景

多窗口流式性能已经有独立 Electron 压力夹具，但正式 `test:release` 仍不会运行聊天压力门禁；
同时结构化编辑卡片的内联 Diff 预览会为完整 patch 创建逐行 DOM，即使卡片只展示一个很矮的预览区。
这两处分别带来“性能回归可能漏过发布”和“大 patch 在普通聊天视图中制造无意义 DOM”的风险。

## 目标

1. 正式发布验证必须包含一段有界的重度多 Agent Electron 聊天性能检查，覆盖 6 个工作区窗口、每个 pane 至少 12 个 tab、至少 20 条同时运行的 Agent 流。
2. 日常发布检查保持可接受时长；现有 5 分钟门禁和 30 分钟 soak 继续用于性能修复与重点发布。
3. Electron 压力测试的真实绘制停顿门槛与既有 `< 500ms` 响应目标一致，不能继续允许接近 2 秒的可见停帧。
4. 结构化编辑卡片的内联 Diff 预览只渲染有界行数；用户打开详情时仍能看到完整 patch。
5. 不改变消息、Provider 上下文、持久化、恢复、Git 内容或用户手动并发能力。
6. 后台 Agent tab 只有消息正文持续变化、tab 标题/图标/状态未变化时，不得迫使整个 pane 重绘；切回该 tab 时仍必须立即显示最新完整内容。
7. 超长助手正文仍在流式增长时不得让整段 Markdown 重解析阻塞新建会话；允许流期间暂用完整纯文本，结束后必须恢复完整 Markdown。

## 验收标准

- `test:release` 的阶段计划中存在独立聊天性能阶段，并在生产 build 成功后运行。
- 发布阶段使用 30 秒压力窗口并复用刚完成的生产 build，不重复构建。
- 手动 `pnpm test:perf:chat:electron` 仍默认运行 5 分钟；`-Soak` 仍运行 30 分钟。
- 压力夹具至少生成 6 个 workspace column、每个 pane 14 个 tab（总计 84 个 tab），并按 `4/4/3/3/3/3` 分布启动 20 个 Agent tab；每列保留一个正在运行的 Agent 为前台，其余 14 条流持续在后台更新。
- 压力期间必须在 20 条流仍同时运行时，循环执行中文输入、焦点、向正在运行的 Agent 延后发送消息，以及在同一排十几个 tab 中切换前台/后台运行 tab。
- 20 条流持续运行时，还必须重复至少 60 次“新建 Agent 会话 tab → 等待新 composer 聚焦 → 立即输入中文 → 切回运行 tab → 再切回新 tab 核对草稿 → 清空并关闭新 tab”，覆盖偶发的新建后数秒无响应，而不是只验证已有 tab。
- 压力夹具的序列化状态至少为 4MB，使用合成历史消息模拟当前打包版约 3MB 的长期状态规模；不得读取或复制用户真实消息内容。
- 延后发送使用应用真实交互与状态路径，但 Provider 由仓库内本地 fake CLI 代替；测试不得联网、调用真实模型或消耗模型 Token。
- 从后台 Agent 切回时必须看到隐藏期间到达的新输出，证明 memo 隔离没有造成旧内容或漏内容。
- 压力夹具的 `frameMaxGapMs` 硬门槛为 500ms；输入、聚焦、延后发送反馈、Tab、数据完整性和崩溃门槛保持不变。
- 新建会话到 composer 可聚焦的 p95 必须小于 500ms、单次最大值也必须小于 500ms；首次中文输入（含自动化键盘调度）的 p95 必须小于 250ms、单次最大值必须小于 500ms，焦点失败次数必须为 0。
- 每个新会话的首次中文草稿在切到运行 tab、再切回新 tab 后仍必须完整，不能用只改 DOM、不提交状态的假输入让门禁变绿；核对后清空并关闭探针 tab，使每次采样都从相同 84-tab 基线开始。
- 长流正文的轻量渲染阈值必须有单测；短流和已完成消息继续走 Markdown，不能永久降级格式。
- 后台普通聊天卡只有 `messages`、草稿、Provider session 等非 tab chrome 数据变化时，`PaneView` memo 比较应视为可复用；标题、Provider、模型、运行状态、未读状态、激活卡及需要保活的 Git 卡变化仍必须触发刷新。
- 内联 Diff 预览最多挂载 80 行；大 patch 的完整文本仍由详情弹层按需渲染。
- 普通小 Diff 的现有内容和顺序不变。
- 新增/调整测试先红后绿；定向测试、质量检查、聊天 Electron 门禁、风险回归和发布验证通过。

## 非目标

- 不做整条 transcript 虚拟化。
- 不修改流式调度参数、React reducer lane 或 Provider 并发。
- 不通过减少并发流、排队启动 Agent 或缩短历史数据来让压力测试变绿。
- 不给 CPU/内存设置未经跨机器校准的硬阈值。
- 不改结构化编辑卡片样式，不盲目更新主题快照。
