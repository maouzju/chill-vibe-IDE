# 计划唤醒 — 需求

## 背景

用户会同时运行多个 Agent，并希望先把后续指令写好，等其他工作完成或到达指定时间后再统一唤醒当前 Agent。现有右键“延后发送”只是在当前回答结束后按 FIFO 逐条发送，不能表达跨 Tab、跨 Agent 或定时触发条件。

## 目标

1. **总开关**：设置页提供“计划唤醒”功能开关，默认打开。关闭时不向普通会话展示新的计划唤醒配置模块；用户明确关闭后的设置继续保留。
2. **逐会话配置**：总开关打开后，普通 Agent 会话的 composer 设置菜单顶部显示计划唤醒模块。每张会话卡可以独立打开/关闭计划唤醒并选择触发模式。
3. **三种模式**：
   - **本工作区其他 Agent 完成**：首条待唤醒消息入队时，记录同一工作区内当时仍在运行的其他 Agent；这些 Agent 都真正完成后，释放前还必须确认本工作区当前没有其他 Agent 仍在运行。等待名单即使因恢复、旧数据或并发更新出现缺失，也不能在仍有运行中 Agent 时提前唤醒。
   - **左侧 Tab 完成**：记录当前 Tab 左侧紧邻的 Agent Tab；它真正完成后释放。没有有效左侧 Agent Tab 时不得武断触发，并明确显示当前不可用。左邻自己也处于待唤醒（有未释放的计时批次）时，同样算作“尚未完成”，必须等它被唤醒、跑完并稳定空闲后才释放，从而支持 `A ← B ← C` 的链式接力。
   - **指定时长**：从当前批次首条消息入队时开始计时，到达用户设置的时长后释放。
4. **真正完成**：Agent 正常结束并保持空闲后才算完成。正常回答结束后若 800ms 内又触发自动鞭策，则中间的短暂空闲不算完成；手动停止、用户打断、终端错误也不算完成。
5. **整批激活**：计时器打开后，用户发送的普通消息和附件进入当前计时批次，不立刻调用 Agent。同一张卡在条件满足前发送的所有消息合并为一个批次；条件满足时，同一时刻释放所有已就绪会话，各会话只启动一个 Agent 回合。合并后的 Provider 请求只包含用户原文与附件，不得注入“待唤醒消息 1”之类内部标签。
6. **可见与可控**：composer 显示待唤醒消息数量、当前条件、整批内容摘要（合并后的用户原文，超长单行截断、悬停看全文；纯附件批次显示“图片消息”并附带图片张数），并提供“立即唤醒”和“取消”操作。“取消”不会丢弃内容，而是按原顺序把待唤醒文字和附件放回输入框；若用户已经开始写下一段草稿，则待唤醒内容放在现有草稿之前并一并保留。还没有自己标题的新会话在有待唤醒消息时，Tab 标题显示“待唤醒”，让用户在不打开该 Tab 时也能看出它在等待；会话拿到自己的标题后，标题优先，工具卡标题不受影响。
7. **随时改条件**（原「配置冻结」，2026-08-15 改）：批次挂起期间用户仍可改唤醒方式和时长，改动立刻对当前批次生效——按新条件重新计算等待目标/到点时间，消息本身不动。待唤醒状态行内就能直接切换三种唤醒方式（duration 另给分钟输入），不必翻设置菜单；设置菜单里的同一组控件也不再禁用。唯一拒绝的切换是 `left-tab` 没有有效左邻：该选项直接禁用并说明原因，不允许切进一个永远不会满足的条件。
8. **持久化**：逐卡开关、模式、时长、待唤醒消息、附件元数据、开始/目标时间和待完成目标均随应用状态保存。重启不会丢消息；到时批次在恢复后仍可释放。
9. **安全关闭**：关闭逐卡计时器或设置总开关不会静默删除现有待唤醒消息。现有批次继续可见，并可按原条件触发、立即唤醒或取消；关闭只阻止新消息进入计时批次。
10. **右键发送即计划唤醒**：会话没有正在回答时右键发送按钮，消息进入该卡的计划唤醒批次而不是立即发出——这覆盖"新会话第一条消息直接右键发送"这个主场景。此时若逐卡开关还没开，自动打开它，且开关与批次必须写在同一次原子更新里，不允许出现"开关亮着但没有批次"或"有批次但开关是关的"。总开关关闭、工具卡、或条件冻结失败（例如 `left-tab` 没有有效左邻）时回退到原有立即发送。会话正在回答时右键保持原有 FIFO 延后发送语义不变。
10A. **替用户开的开关用完就关**（2026-08-16 加）：由第 10 条自动打开的逐卡开关只对那一批负责。批次被释放、立即唤醒或取消后，开关必须自动关回去，该卡回到普通发送。用户自己在设置里拨开的开关不受影响，继续按第 5 条持续攒消息，直到用户手动关闭。区分靠一个显式来源标记，不靠猜；旧存档没有这个标记时一律当作"用户显式开启"，宁可少关一次也不能把用户手动开的计时器悄悄关掉。
11. **记住上次的唤醒方式**：用户在会话设置菜单里选过的唤醒条件与时长成为全局默认，新开的会话 Tab 直接沿用上一次的选择，不再每次回到"其他 Agent 完成 / 30 分钟"。已经存在的会话不受影响（与默认模型只喂新卡的语义一致）。看板 MCP 等自动化路径写入的模式不算用户偏好，不得污染这个默认值。
12. **兼容现有发送行为**：
    - 本地斜杠命令继续立即执行，不进入计时器。
    - ask-user 回答继续立即停止等待中的 stream 并发送，避免把解锁回答排进计时器后形成死锁。
    - 已有历史或原生会话上的空输入“继续会话”属于普通用户发送；逐卡计时器开启时必须进入待唤醒批次，不能绕过计时器立即运行。
    - 自动鞭策生成的消息和计时器自身释放的批次绕过计时器，避免递归排队。
    - 普通右键延后发送队列保持原有语义，不与计时批次混用。
    - 工具卡不显示或使用计时器。

## 验收标准

- 旧存档缺少新字段时可正常打开，计划唤醒总开关默认打开、逐会话开关与队列仍为空；旧存档中明确保存的关闭值继续保持关闭。
- 首条消息入队时正确冻结三类触发数据，后续消息加入同一批次。
- 工作区模式只等待同工作区、当时正在运行、非工具卡的其他 Agent。
- 工作区模式释放前再次扫描同工作区；只要仍有其他 Agent 在运行，即使持久化等待名单为空也不得释放。
- 左侧模式只绑定同 Pane 直接左邻的 Agent Tab。
- 自动鞭策造成的短暂 idle 不释放批次；最终稳定完成后释放。
- 多张卡在同一次完成/到时检查中就绪时，先原子清空各自持久化批次，再并发启动各卡的合并请求，避免重复发送。
- 释放给 Provider 的文本保持用户原文；多条文本只用空行连接，不暴露内部排队标签。
- 取消待唤醒批次后，原文字与附件回到 composer；已有草稿和草稿附件不被覆盖或删除。
- 空输入“继续会话”可作为显式待唤醒项持久化并在条件满足后继续原会话；没有显式继续标记的普通空队列项仍视为无效并在恢复时丢弃，不能再次造成存档校验崩溃。
- light/dark 与桌面/窄屏下，模块、禁用态、焦点态和待唤醒状态可读且不溢出。
- 无标题会话排入待唤醒消息后 Tab 标题变为“待唤醒”，批次释放或取消后回到“新会话”；已有标题的会话与 Git/Brainstorm 等工具卡标题保持不变。
- 空闲会话右键发送进入待唤醒批次并同时打开逐卡开关；正在回答的会话右键仍走 FIFO 延后发送；总开关关闭时右键回到原来的立即发送。
- 改过唤醒条件或时长后新建的会话 Tab 直接带上该条件与时长；已打开的会话保持原值。

## 非目标

- 不提供跨工作区目标选择器。
- 不允许对同一批次逐条重排。
- 不在一张会话卡内同时启动多个 Provider stream；同卡多条消息会合并为一个 Agent 回合。
- 不把计时器做成系统级后台任务服务；它依赖 Chill Vibe 运行或下次恢复。
